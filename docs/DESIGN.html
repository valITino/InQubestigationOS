02Distribution policy: Debian everywhere possible

verified dom0 is Fedora and cannot be changed

Qubes OS builds dom0 on Fedora and ships no Debian dom0. On 4.3 that is Fedora 41. This is architecture, not a setting — there is no flag, no build option. Everything the image actually runs, however, is Debian.

Why Debian service qubes are safe

Verified against upstream rather than assumed. The Qubes Debian template installs qubes-vm-recommended, which depends on qubes-core-agent-networking, qubes-core-agent-network-manager and qubes-usb-proxy — exactly what sys-net, sys-firewall and sys-usb need. The template's own package list carries firmware-linux, network-manager and nftables. The provisioner installs these explicitly anyway, so a minimal Debian base works too.

decision Check Wi-Fi on the issued NIC before rollout

Qubes gives most qubes a dom0-provided kernel, so NIC drivers come from Fedora regardless. Firmware blobs, however, are read from the template filesystem. debian-13-xfce is built with the firmware option and the provisioner adds firmware-linux and firmware-iwlwifi, but Debian firmware can lag Fedora's. This is the one place the Debian switch could bite. Test it on the actual laptop model.

What this buys: one distribution across the estate, one package manager, one update cadence, one Wazuh repository type, one advisory feed. The dnf path is gone from the provisioner except for the Fedora template itself, which is now optional (use_fedora_template defaults to false — it still receives an agent, since the requirement was an agent in every template).

03Network topology

The one rule of this image: there is exactly one road to the internet, and it runs through four orange checkpoints. Every clearnet qube — office, casework, tooling, even the SIEM — has sys-proxy as its netvm and no way around it. The single exception is the purple branch: Tor traffic joins at sys-firewall, bypassing proxy, IPS and DPI, because inspecting Tor is pointless and logging it against your own identity is harmful.

04The egress chain, hop by hop

Order is not cosmetic. The proxy sits first because every Qubes hop NATs — place it later and its logs would show the previous hop's address instead of the originating qube's. Being hop one makes it the attribution record. The IPS sits before the DPI so Zeek only records traffic that was allowed to exist. The firewall sits last as the single choke point owning DNS and segmentation for both branches.

sys-proxy

Transparent Squid intercept. Logs every HTTP request and every TLS connection (SNI only, no decryption) with the originating qube's IP — this hop is the attribution record. Non-web TCP and UDP pass through unmodified but still traverse the rest of the chain.
tpl-proxy · netvm sys-ids · provides_network · 80→3128, 443→3129 · custom-dnat-squid + custom-input

sys-ids

Suricata inline via NFQUEUE with drop verdicts — a real IPS, not a logger. Fail-closed: if Suricata dies the chain stops forwarding rather than passing traffic uninspected. ET Open ruleset, drop policy on high-confidence exploit and C2 categories only.
tpl-ids · netvm sys-dpi · queue num 0 (no bypass) · eve.json → Wazuh

sys-dpi

Zeek 8.0 LTS in passive deep-inspection mode: connection records, DNS, HTTP, TLS fingerprints, SSH, extracted file hashes, x509. This is the flight recorder — when a case asks what a machine talked to in March, the answer lives here and in the SIEM.
tpl-ids · netvm sys-firewall · /opt/zeek · logs → Wazuh

sys-firewall

Single choke point for both branches. Forces every clearnet DNS packet into a local validating resolver speaking DNS-over-TLS to Quad9. Enforces the inter-qube segmentation matrix. The Tor branch attaches here and is exempt from the DNS rules by design.
tpl-sys · netvm sys-net · unbound → 9.9.9.9:853 · dnat-dns replaced via qubes-firewall.d

sys-net

Holds the physical NIC via PCI passthrough, speaks DHCP to whatever hostile network the laptop is on, and is treated as compromised by default. Nothing terminates here; it only forwards.
tpl-sys · netvm none · PCI NIC attached

Internet

Clearnet exits carry the unit's address and full inspection records. Tor exits carry a Tor exit node's address and no local content records — two cleanly separated postures, chosen per task by picking the qube.
clearnet: attributed + inspected · Tor: anonymous + uninspected

07Firewall implementation

This section was rewritten after verification against the official Qubes firewall documentation and two upstream issues. The previous revision would have failed silently in three separate places.

corrected There is no custom-prerouting chain

The Squid redirect was written into a chain that does not exist. The documented user hooks are custom-forward and custom-input only; for NAT you must create your own chain. A request to add a custom-nat chain is still open upstream (qubes-issues #8629).

corrected Squid would have received nothing

Redirected packets terminate locally on sys-proxy, so they take the input path, not forward. The old rules only touched forward chains — traffic would have been dropped one hop before Squid, with every config file looking correct. The custom-input accept below is the fix.

sys-proxy — intercept

sys-proxy · /rw/config/qubes-firewall-user-script
#!/bin/sh
# Create our own nat chain — the documented pattern from the Qubes firewall
# docs. Idempotent: 2>/dev/null swallows "chain exists" on restart.
nft add chain ip qubes custom-dnat-squid \
    '{ type nat hook prerouting priority filter + 1 ; policy accept; }' 2>/dev/null

# Redirect downstream web traffic into Squid. Other ports are untouched and
# continue up the chain, still inspected by Suricata and Zeek.
nft add rule ip qubes custom-dnat-squid iifname "vif*" tcp dport 80  redirect to :3128
nft add rule ip qubes custom-dnat-squid iifname "vif*" tcp dport 443 redirect to :3129

# Without this the redirected packets never reach the Squid sockets.
nft add rule ip qubes custom-input iifname "vif*" tcp dport { 3128, 3129 } counter accept

# Sibling qubes meet here first: agent traffic to the SIEM, nothing else.
nft add rule ip qubes custom-forward ip daddr 10.137.0.50 tcp dport { 1514, 1515 } counter accept

sys-firewall — DNS enforcement

corrected DNS rules were written into a chain Qubes regenerates

The old code ran nft flush chain ip qubes dnat-dns from the user script. Two problems: modifying Qubes-managed chains is explicitly unsupported, and qubes-setup-dnat-to-ns rewrites dnat-dns when the network comes up, silently discarding the rules. DNS enforcement would have appeared configured and quietly not applied — the worst failure mode in the whole design, because it looks fine until someone audits egress.

The working pattern (qubes-issues #9056) replaces the chain wholesale from an nft -f script in /rw/config/qubes-firewall.d/, which runs as part of qubes-firewall startup:

sys-firewall · /rw/config/qubes-firewall.d/10-golden-dns (mode 0755)
#!/usr/sbin/nft -f
# mode: dot — redirect downstream DNS to the local unbound, which forwards
# over TLS to 9.9.9.9. Query contents never cross the wire in clear.
#
# The Tor branch is exempt STRUCTURALLY: sys-whonix resolves inside Tor and
# never emits port 53 toward this qube. DO NOT add DNS rules for it. Ever.
add chain ip qubes dnat-dns
delete chain ip qubes dnat-dns
table ip qubes {
    chain dnat-dns {
        type nat hook prerouting priority dstnat; policy accept;
        iifname "vif*" meta l4proto { tcp, udp } th dport 53 redirect to :53
    }
}

redirect rather than dnat to 127.0.0.1 avoids needing route_localnet. The add-then-delete idiom guarantees the delete succeeds whether or not the chain already exists.

sys-firewall · /rw/config/qubes-firewall-user-script
#!/bin/sh
# Let downstream DNS reach the local resolver after the redirect above.
nft add rule ip qubes custom-input iifname "vif*" meta l4proto { tcp, udp } th dport 53 counter accept

# Nothing raw on port 53 leaves upstream: kills clients with hardcoded
# resolvers. Legitimate queries were already translated and never reach here.
nft add rule ip qubes custom-forward meta l4proto { tcp, udp } th dport 53 counter drop

# Segmentation: qube-to-qube stays denied except the SIEM flows above.
nft add rule ip qubes custom-forward ip saddr 10.137.0.0/16 ip daddr 10.137.0.0/16 counter drop
nft add rule ip qubes custom-forward ip saddr 10.138.0.0/16 ip daddr 10.137.0.0/16 counter drop

08Middlebox configuration

Everything below persists across qube reboots via bind-dirs or /rw/config; nothing lives only in a running AppVM.

Squid — peek, do not decrypt

Squid runs in intercept mode: web traffic is redirected into it invisibly, everything else flows past. TLS is peeked, then spliced — Squid reads the SNI hostname and passes the encrypted stream on untouched. Full interception with a unit CA in every template is possible but is a legal and procedural decision, not a technical default; the hooks are present and left off.

tpl-proxy · /etc/squid/squid.conf (core directives)
http_port  3128 intercept
https_port 3129 intercept ssl-bump generate-host-certificates=off \
           tls-cert=/etc/squid/placeholder.pem

acl step1 at_step SslBump1
ssl_bump peek step1        # read the SNI
ssl_bump splice all        # pass through encrypted — NO decryption

acl localqubes src 10.137.0.0/16 10.138.0.0/16
http_access allow localqubes
http_access deny all
cache deny all             # investigators do not want cached evidence

logformat attrib %ts.%03tu %>a %Ss/%03>Hs %rm %ru %ssl::>sni
access_log daemon:/var/log/squid/access.log attrib
verified A certificate is required even for splice-only

squid-openssl is present in Debian 13 (Squid 6.13) and is the SSL-Bump-capable build; it cannot be co-installed with plain squid. Even when only splicing, the ssl-bump port needs a tls-cert= present so Squid can parse the ClientHello — hence the self-signed placeholder, which is never used to sign anything. %>a is the attribution field: the originating qube's address.

Suricata — inline IPS, fail-closed

sys-ids · /rw/config/qubes-firewall-user-script
#!/bin/sh
# Every forwarded packet is queued to Suricata for an accept/drop verdict.
# Deliberately NO "bypass": Suricata down means the chain stops.
nft insert rule ip qubes custom-forward counter queue num 0
decision Fail-closed over availability

Without bypass, the kernel drops packets when nothing is listening on the queue. A Suricata crash therefore halts the inspected chain rather than passing traffic uninspected. Restart=always with RestartSec=2 bounds the outage to seconds. Setting ips_failure_mode: "open" adds bypass and reverses this — change it knowingly, not by accident.

Zeek — flight recorder

# /opt/zeek/etc/node.cfg
[zeek]
type=standalone
host=localhost
interface=eth0     # post-IPS; per-qube attribution lives in the Squid log

# /rw/config/qubes-bind-dirs.d/50_golden_dpi.conf
binds+=( '/opt/zeek/etc' )
binds+=( '/opt/zeek/logs' )

Because each Qubes hop NATs, Zeek on eth0 sees what left the chain but not which qube sent it. Per-qube attribution comes from Squid (pre-NAT, hop one) and from the endpoint agents. Zeek 8.0 is the current LTS line; it will not jump to a new LTS on its own, which matters when the logs are evidence.

unbound — DNS over TLS

sys-firewall · /etc/unbound/unbound.conf.d/golden-image.conf
server:
    interface: 0.0.0.0
    access-control: 127.0.0.0/8    allow
    access-control: 10.137.0.0/16  allow
    access-control: 10.138.0.0/16  allow
    access-control: 0.0.0.0/0      refuse   # not an open resolver
    do-not-query-localhost: no
    tls-cert-bundle: /etc/ssl/certs/ca-certificates.crt
forward-zone:
    name: "."
    forward-tls-upstream: yes
    forward-first: no                    # never fall back to cleartext
    forward-addr: 9.9.9.9@853#dns.quad9.net
    forward-addr: 149.112.112.112@853#dns.quad9.net

The addr@port#hostname form pins the certificate name. Investigator DNS queries are themselves sensitive metadata and should not cross the wire in plaintext. DoH cannot be fully blocked without breaking the web; Suricata's ruleset flags known DoH endpoints instead, giving detection where prevention is impractical.

bind-dirs

corrected Agents would have lost their identity every reboot

/var/ossec was declared in bind-dirs, but /rw/bind-dirs/var/ossec was never seeded. When the directory does not already exist there, the first-boot copy fails and the agent re-enrolls as a new agent on every reboot — quietly filling the SIEM with duplicate hosts. The provisioner now pre-creates it. File names also follow the documented NN_name.conf convention.

# /rw/config/qubes-bind-dirs.d/50_golden_wazuh.conf
binds+=( '/var/ossec' )

# run once before the bind takes effect:
mkdir -p /rw/bind-dirs/var
[ -d /rw/bind-dirs/var/ossec ] || cp -a /var/ossec /rw/bind-dirs/var/ossec

09Wazuh SIEM

Coverage is total: every template ships the agent, every running qube enrolls under its own name, so the dashboard shows per-compartment telemetry rather than one blurred host. Two transports exist because the purple branch must never speak clearnet.

decision Version pinning is not optional

Wazuh guarantees compatibility only when the manager version is at least the agent version. Every template here updates weekly, so an unpinned agent would eventually overtake the manager and every agent on the laptop would stop reporting — silently, on an unpredictable date, most likely discovered when someone went looking for evidence that was never collected. For an investigator workstation that is the worst possible failure: monitoring that looks healthy and is not.

applied in every template
apt-get install -y wazuh-agent
systemctl disable wazuh-agent                      # templates never beacon
echo "wazuh-agent hold" | dpkg --set-selections    # freeze the version
sed -i 's|^deb |#deb |' /etc/apt/sources.list.d/wazuh.list

Upgrade order when the time comes: wazuh-srv first, then release the holds and upgrade the agents. Never the reverse. Acceptance test 4b asserts the hold is present across all Debian templates.

The build uses Wazuh's documented password-authentication flow rather than agent-auth, because a golden image wants configuration that re-applies cleanly rather than a registration action that fires once.

11Weekly backup

corrected qvm-backup has no --yes flag

The previous revision's timer would have hung waiting for confirmation, every Sunday at 03:00, forever — the kind of failure nobody notices until they need a restore. Profile mode is the documented non-interactive path, and --profile is mutually exclusive with all other options.

include:
 - dom0

 - wazuh-srv

The wrapper regenerates this file before each run so current case-* qubes are picked up, then calls qvm-backup --profile golden-image. A systemd timer fires it weekly.

Scope and discipline

  • Included: everything carrying state or effort — vault, work qubes, case qubes, kali-clear (tool configs and Maltego graphs live in /home), wazuh-srv (standalone, so full root), all custom templates, and dom0.
  • Excluded: stock templates (re-downloadable), untrusted, and the entire Tor branch — it intentionally holds nothing, and backing it up would copy anonymous-context artifacts into attributed storage.
  • Retention: the last four weekly sets.
  • Monthly: restore verification, calendared, owned by a named person. An unverified backup is a hope, not a control.
  • Escrow the passphrase before shredding credentials.json. No passphrase, no restore.

Kali — the fingerprint is the check that matters

verified 827C…E4C5 is the current key, not a retired one

This is worth stating plainly because it is easy to misread. 827C8569F2518CC677FECA1AED65462EC8D5E4C5 is the current 2025 key: rsa4096, created 2025-04-17, expires 2028-04-17, short id ED65462EC8D5E4C5. The retired key is 44C6513A…ED444FF07D8D0BF6 (expires 2027-02-04), still shipped in the keyring so older releases verify. The April 2025 breakage happened because the archive stopped being signed by the old key and systems lacked the new one — not because the new key was withdrawn.

827C8569F2518CC677FECA1AED65462EC8D5E4C5   # CURRENT — Kali Archive Automatic Signing Key (2025)
44C6513A8E4FB3D30875F758ED444FF07D8D0BF6   # retired, still shipped · expires 2027-02-04
603374c107a90a69d983dbcb4d31e0d6eedfc325   # SHA1 of the keyring file, published 2025-04-28

deb [signed-by=/usr/share/keyrings/kali-archive-keyring.gpg] \
    https://http.kali.org/kali kali-rolling main contrib non-free non-free-firmware

The build treats the fingerprint as authoritative and the checksum as advisory. A fingerprint identifies the key and only changes when Kali rolls one — a mismatch stops the build. A checksum identifies the file and changes whenever the keyring is regenerated for any reason — a mismatch warns and asks you to re-verify. Getting this the wrong way round produces either false alarms or false confidence. The repository line now pins trust with signed-by= rather than relying on the global trust store.

Zeek — you are trusting the build service

Zeek is not in Debian main; upstream ships binaries through the openSUSE Build Service, and Zeek state plainly that OBS signs these packages outside the Zeek project's control. Their documentation also warns that on Debian you must re-add the key manually when it expires. That belongs on the monthly checklist: an expired key silently stops Zeek updates, and a DPI recorder that quietly goes stale is worse than one that fails loudly.

Tier 2 is the right answer for air-gapped deployment or colleagues without reliable connectivity at install time. Otherwise Tier 1 gives a far smaller image and one maintenance track instead of two. Provisioning still runs on Tier 2 — the ISO ships templates, not topology.

decision Three things before you distribute an ISO

A self-built ISO is not signed by the Qubes team. Colleagues cannot verify it against the Qubes release key, because it is not a Qubes release. You become the signing authority: sign with the unit key and distribute that fingerprint through a channel independent of the ISO. An unsigned image on USB sticks is exactly the supply-chain problem this design exists to prevent.

The ISO goes stale and becomes a liability. It freezes dom0, Xen and the kernel at build time. An image built today and installed in six months installs six months of known-vulnerable dom0 before its first update. Rebuild on every security bulletin affecting dom0 or Xen; treat a stale investigator ISO as unusable.

No credentials are baked in. They are generated per machine at provisioning. A shared secret inside a widely-copied image across a whole unit would be the worst possible outcome.

Credentials

Four secrets — dashboard, API, agent enrollment, backup passphrase — generated uniquely per machine into ~/golden-image/credentials.json, mode 600, dom0 only, with rotation procedures beside it. Log in, change them, escrow the new values, then shred -u the file. A use_fixed_defaults option reproduces shared-password behaviour for an isolated lab; it warns, stamps the file, and the acceptance tests flag it.
